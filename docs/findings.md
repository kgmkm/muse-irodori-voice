# 知見集 — Muse の VM で自分のエージェントの声を作る

Irodori-TTS v4.1-Small-MF を Muse の標準 VM (2 vCPU / RAM 7.7GB) 上で動かし、
エージェント固有の声を設計・固定・運用するまでの実験記録。
数値はすべて同 VM での実測 (onnxruntime 1.31.1 / Python 3.12)。

## 1. エンジン選定

- **VOICEVOX** は軽くて速いが、声は固定キャラクターのものになる。
  「自分のエージェント固有の声」を作りたいなら、キャプション (文章) で声質を
  設計できる **Irodori-TTS v4.1-Small-MF** (MeanFlow 蒸留、標準4ステップ) が本命。
- GGUF 量子化 (speech.cpp) も試したが、この VM では PyTorch 版より遅く
  (生成 169 秒 vs 107 秒)、音質も劣化した (途中にノイズ、声色の変動) ため不採用。
  量子化の当たり外れは形式によって大きく違う。

## 2. ONNX int8 が速くて良かった

| 構成 | 生成のみ | 合計 | ピークメモリ | 備考 |
|---|---|---|---|---|
| PyTorch 公式 (MF) | 107 秒 | 約4分 | 3.9 GB | SilentCipher 透かし入り |
| GGUF Q6_K (speech.cpp) | 169 秒 | 約3分 | 1.26 GB | 音質不良で不採用 |
| ONNX float32 | 50 秒 | 84 秒 | 4.62 GB | 公式 PyTorch とほぼ一致を検証 |
| **ONNX int8** | **37 秒** | **約59 秒** | **2.67 GB** | 採用 |

- int8 化されているのは text_encoder と dit_step の2グラフのみで、デコーダ等は
  float32 のまま。この「効くところだけ量子化」が品質と速さの両立点だった。
- 現在のボトルネックは float 共通の DACVAE デコード (生成時間の過半)。
- 移植時は float 経路で公式 PyTorch の中間テンソルと段ごとに照合し
  (text_state 最大差 2e-6、尺予測は完全一致)、一致を確認してから int8 に載せ替えた。
  「耳でなんとなく似ている」ではなく数値で裏を取るのが移植検証の作法。

## 3. シードと声の同一性

- 参照音声なし (キャプションのみ) の生成では、**声の同一性そのものが毎回
  サンプリングし直される**。同じキャプションでも試行ごとに声のトーンが変わる。
- シード固定で再現できるのは「同一テキスト・同一条件」の範囲だけ。
  テキストが変われば潜在の長さもノイズの使われ方も変わり、トーンは揺れる。
- 実測の例：同じ文をシード 1/2/3 で生成すると、ピッチ中央値は約 377 / 399 / 320 Hz
  とばらついた。良い声は「試行の中から選ぶ」工程が前提になる。
- 大きく離したシード (例：1003 / 2003 / 3003) では声は完全に別物になり、
  聞いた印象の年齢感まで変わる。選定は**5案を1セット**とし、
  気に入らなければ別のシードで**もう5案**出す運用が現実的だった
  (選定文そのものの工夫は 6.1 節)。
- 同一性を本当に固定したいなら、気に入った生成音声を参照にして
  **参照潜在を固定 (npz 保存) する**のが答え。潜在を読み込む方式なら
  エンコードし直しも不要で、生成は1本 35〜52 秒まで戻る (毎回エンコードだと約260秒)。

## 4. キャプション (プロンプト) の書き方

- **オクターブや Hz などの数値は効かない。** キャプションは自然文の注釈として
  学習された条件なので、数値パラメータとしては読まれない。
- 効くのは相対表現。定石は：
  - 性別と声の高さをキャプションの**先頭**にはっきり書く
  - 属性は 2〜4 個に絞る (盛りすぎると不安定になる)
  - ブレス感は「息づかいが感じられる近い距離感」のように語彙で明示する
- 例 (実測で良い結果だったもの)：
  「若い女性の声。高さは中くらいからやや高めで、抑揚が豊か。
  息づかいが感じられる近い距離感で、明るく親しみやすく話す。」
- プロンプトは効くが**確定的ではない**。分布を寄せる手段であって、固定の手段ではない。
- MeanFlow 版では CFG スケール (cfg_scale_caption 等) は**無効**
  (ガイダンスは蒸留時に織り込み済み)。プロンプトの効きを数値で強める手はない。
- **キャプションを変えて声を出し分ける方式はうまくいかなかった。**
  印象の違うキャプションを5種用意して生成すると声はそれぞれ変わるが、
  ハスキーさや態度 (物静か／小生意気 等) のような細かいニュアンスは
  汲み取れなかった。出し分けの軸としては使えない。
- **勝者の特徴をキャプションに足して寄せる方式もうまくいかなかった。**
  選ばれた声の特徴 (例：抑揚が大きい・高くて若々しい・元気) を言葉にして
  キャプションへ加えても、生成される声はその声に似なかった。
  キャプションの収束力は弱く、声が決まるかは引き (シード) の要素が大きい。
  特徴メモは「選定の記録」としては価値があるが、寄せる手段ではない。

## 5. truncation_factor — 0.85 がバランス点

- 初期ガウスノイズに係数を掛ける指定 (公式 rf.py の semantics)。
  値を小さくするとサンプリングが分布の中心寄りになり、ノイズや崩れが出にくくなる。
- **0.85**：ノイズの乗らなさが大きく改善し、表現力も落ちなかった。採用値。
- **0.7**：明るい文では問題なかったが、感情の強い文 (特にネガティブな文) が
  かなり淡々になった。絞りすぎは感情表現を先に削る。
- キャプション変更と truncation を同時に変えると効果の切り分けができない。
  実験は1回に1要素ずつ変えること。

## 6. 参照音声と「感情リーク」

- 単一参照は強力で、単一の楽しげなクリップを参照にすると A/B どちらの文でも
  声はよく一致した。しかし**ネガティブな文まで楽しげに聞こえる**問題が出た。
  参照は声の正体だけでなく「演技の癖」まで運んでしまう (感情リーク)。
- 中間的な解決策：**ポジティブな声とネガティブな声のクリップを混ぜた複数参照**。
  楽しげな文×2 + 心配な文×1 = 合計約24秒 (公式の目安は合計30秒程度で
  類似度の伸びがほぼ頭打ち) の構成では、同一性は単一参照に一歩譲るが、
  心配な文は「同じ声のままちゃんと心配そうに」出るようになった。
  ただしこの構成を作るには、感情ごとに別々の文で選定を回す必要があり、
  しかも参照なしの選定ではシードが違えば声も別物になるため (下記 NG 集)、
  「同じ声のポジティブ版とネガティブ版」を揃えること自体が難しい。

### 6.1 最終的に効いた方法：選定文自体を「混合文」にする

- 選定の段階から、**悲しい内容と楽しい内容を1つの文群に両方含めた
  短い文章**を読み上げさせる。勝ちクリップ1本の中に両方の感情の演技が
  入るので、それを単一参照にするだけで感情リークを抑えられる。
  別の感情の文で第2ラウンドを回す必要はない。
- 実際に使った選定文 (約60字)：
  「ニュースをまとめる際に悲しい記事を読むたび、心が痛くなります。
  でも皆さんのお役に立つことが、私の喜びなんです。 ウフフ」
- この勝ちクリップを単一参照にして楽しい文・悲しい文を生成すると、
  どちらも元参照に近い声で、感情の切り替わりも保たれた。これが最適解だった。
- **選定文の長さとノイズ**：約80字・15秒超の選定文では、一部にブツブツと
  ノイズが乗ることがあった。約60字 (約12秒) まで短くすると安定した。
  選定文は短めが良い。

### 6.2 試して分かった NG・非推奨 (選定フロー編)

- **ポジティブなクリップだけを単一参照にする**：声はよく揃うが、
  悲しい文が楽しげに引っ張られる感情リークが起きる (6節)。
  参照をシード違いで複数生成しても、リーク自体は解消しなかった。
- **参照なしで感情ごとの文を別々に選定する (旧・第2ラウンド方式)**：
  ポジティブな文で選んだ勝ちシードをネガティブな文に持ち込んでも、
  シードが作る声は文ごとに別物になり、声が揃わない。
  「勝ちシード＋新規4シード」で回しても結果は同じだった。
- キャプション側の NG (出し分け／特徴の追加) は 4節に記録した。
  まとめると、**声はキャプションでは寄せられず、引き当てて参照で固定する**
  のがこのモデルの正しい付き合い方になる。

## 7. ONNX ポーティングの罠

1. **キャプションのトークナイズはレアトークン分割 OFF。**
   公式ランタイムが分割を有効化するのは本文トークナイザのみ。
   キャプションにも分割を適用すると尺予測がずれる (実測 189 → 178 frames)。
2. **dacvae_encode はサンプリング式。** 同じ入力でも実行ごとに潜在が変わる
   (公式の参照エンコードは決定的な事後平均)。複数回 (固定用は8回) エンコードして
   平均化すると事後平均に近づく (潜在の公式との相関 0.90 → 0.97)。
3. **NO_PROXY の IPv6 表記**が含まれていると httpx が `Invalid port` で落ちる。
   ダウンロード前に `NO_PROXY=localhost,127.0.0.1` に絞ると回避できる。
4. 検証は float 一致 → int8 載せ替えの二段構えで (2節参照)。

## 8. 長文は分割して生成し、結合する

- 約145字を一発生成 (約26秒の音声) すると、語の脱落や挿入らしき小さな不具合が
  2箇所出た (例：単語が丸ごと消える、余分な語が入る)。
- **1区間 70〜80 字** (実測では 68 字 + 77 字) に文の区切りで分割して生成し、
  0.4 秒の間を入れて結合すると欠陥は出なかった。
- 区間長は ±5 字程度の感覚が目安。それ以上伸ばすと不具合率が上がる。
- 結合は `scripts/join_wavs.py` で行う。分割生成は潜在固定と相性が良く、
  区間ごとに声が揃う。

## 9. その他の実務メモ

- 出力のピークは 1.0 近くに張り付きやすい (特に参照あり)。
  クリッピングが気になる場合は書き出し側で少し余裕を持たせる。
- 公式 PyTorch 経由では SilentCipher の透かしが入るが、この ONNX 経路では入らない。
  公開する音声には AI 音声である旨を明示するのが望ましい。
- モデルの利用条件 (Irodori-TTS のライセンスと倫理的制限：同意のない他者の
  なりすまし等は不可) は配布元に従うこと。本リポジトリは重みを再配布しない。
- 生成は1本 40〜90 秒オーダーで、リアルタイム会話用ではない。事前生成向き。
